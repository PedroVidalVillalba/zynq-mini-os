# Mini-OS for the Zynq-7000

A minimal preemptive multitasking kernel for the ARM Cortex-A9 in the Xilinx Zynq-7000 SoC, running bare metal on a ZedBoard. It runs three user programs concurrently in User mode, switching between them in round-robin order on every 1 ms timer interrupt.

Developed as the mini-project of _Computer System Design_ (COSE321) at Korea University.

## How it works

### Initialization (Supervisor mode)

`main.S` takes over after the board support package's startup code:

1. Disables interrupts and sets up separate stacks for IRQ and Supervisor modes.
2. Points the Vector Base Address Register (VBAR) at its own vector table, which routes IRQs to the kernel's interrupt handler.
3. Calls `init()` (`scheduler.c`), which:
   - initializes the UART at 115 200 bps, 8N1;
   - enables the Generic Interrupt Controller (GIC) distributor and CPU interface, and enables interrupt 29 (the private timer);
   - creates a process for each user program;
   - starts the private timer with a 1 ms period in auto-reload mode.
4. Enables interrupts and drops to User mode, waiting with `wfi` until the first tick.

### Processes

Each process has a control block in a fixed-size process table (`process.c`) holding its 16 general-purpose registers (r0–r15), its status register, and its stack. A new process starts with its program counter at the program's entry point, its stack pointer at the top of its own 16 KiB slice of the user stack area, and a status register selecting User mode with FIQs masked.

### Context switch (IRQ mode)

On every timer interrupt, the IRQ handler in `main.S`:

1. Saves the interrupted process's User-mode registers r0–r14 (using `stm` with the `^` suffix to access User-mode banked registers from IRQ mode), its return address and its SPSR to a fixed `saved_state` area.
2. Calls the C handler `irq_isr()`, which reads the interrupt ID from the GIC, dispatches the timer interrupt to the scheduler, clears the timer's status flag, and signals end-of-interrupt to the GIC.
3. The scheduler copies `saved_state` into the current process's control block and loads the next process's registers into `saved_state`, in round-robin order (task 1 → task 2 → task 3 → task 1 …).
4. Restores all User-mode registers and the SPSR from `saved_state` and returns with `movs pc, lr`, resuming the next process exactly where it was interrupted.

Because the handler always saves to and restores from the same `saved_state` area, the assembly code is independent of the scheduling policy, which lives entirely in C.

### Memory layout

| Region | Size | Used by |
|---|---|---|
| IRQ stack | 4 KiB | Interrupt handler |
| Supervisor stack | 4 KiB | Initialization |
| User stack area | 64 KiB | Split into 16 KiB per process (up to 4 processes) |

## Source files

| File | Contents |
|---|---|
| `main.S` | Vector table, mode and stack setup, IRQ entry and exit with full context save/restore |
| `scheduler.c` | System initialization, round-robin scheduler and top-level IRQ dispatcher |
| `process.c/h` | Process control blocks: creation, removal and context switching |
| `gic.c/h` | Generic Interrupt Controller driver |
| `private_timer.c/h` | Cortex-A9 private timer driver |
| `uart_init.c`, `uart_print.c`, `uart.h` | UART driver: initialization, character and string output, and `uart_printf`, a `printf` subset supporting flags, width and the `d i b o u x c s p %` conversions |
| `peripheral_regs.c/h` | Memory-mapped register addresses for the GPIO, UART, private timer and GIC |
| `lscript.ld` | Linker script generated by Vitis for the Cortex-A9 |

### User programs

The kernel runs three user programs with the entry points `task1_c`, `task2_c` and `task3_c`. They were provided by the course and are **not included** in this repository:

- **Task 1** repeatedly selection-sorts an array and shows the result on the board's LEDs.
- **Task 2** runs the Dhrystone benchmark, printing the name of each procedure over the UART.
- **Task 3** prints a greeting over the UART.

Any C functions with the signature `int task(void)` that never return can take their place: add their files to the project and register them with `process_new()` in `init()`.

## Building and running

The project was developed with AMD Xilinx Vitis 2021.1 for a ZedBoard, using a hardware platform exported from Vivado with the processing system and the GPIO peripheral for the LEDs.

1. In Vitis, create a platform from the hardware design (`.xsa`) with a standalone domain for `ps7_cortexa9_0`.
2. Create an empty C application project on that platform.
3. Copy the files from this repository, plus the three user programs, into the application's `src/` folder.
4. Build the project, program the FPGA with the bitstream, and run the application on the board.
5. Open a serial terminal on the board's USB-UART at 115 200 bps, 8N1, to see the output of tasks 2 and 3, while the LEDs show task 1.

## Limitations

- Only general-purpose registers and the status register are saved on a context switch. The floating-point (VFP/NEON) registers are not, so user programs must not use floating-point arithmetic.
- All processes share the UART without any locking, so output from different tasks can interleave mid-line when a task is preempted while printing.
- The process table holds at most 4 processes, all of them with the same priority, and the round-robin order is fixed to the three tasks created at start-up.
- User programs run in ARM state; Thumb code is not supported as an entry point.
- There are no system calls: processes cannot yield, sleep or exit.
